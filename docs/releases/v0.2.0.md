# Crucible DB v0.2.0

Released on 11 September 2026.

Crucible DB v0.2.0 adds governed native PostgreSQL and MySQL client access, makes the control database portable across SQLite, PostgreSQL, and MySQL, and strengthens the application-database migration and production release workflows. It also ships a more compact administration experience and broader security and compatibility coverage.

## Highlights

### Governed native client access

- Connect `psql`, the MySQL CLI, and compatible desktop clients through the Crucible CLI's loopback-only tunnel.
- Issue short-lived credentials from an approved Query Access session without exposing target-database credentials to the user.
- Apply the approved role, database scope, access mode, SQL policy, audit, and expiry controls to every protocol statement.
- Close active connections when a lease is revoked and retain durable heartbeat and connection activity in the control plane.
- Keep the native proxy private: its PostgreSQL, MySQL, and tunnel listeners are not published as host ports.

The automated compatibility matrix qualifies matching `psql` 14–18 and MySQL CLI 8.0/8.4 executables. It also exercises metadata discovery, prepared and binary protocol flows, transactions, denial recovery, reconnect, cancellation where supported, and live revocation. See the [native client compatibility reference](../reference/native-client-compatibility.md) before selecting a desktop client.

### Portable application database

- Store Crucible control-plane data in SQLite, PostgreSQL, or MySQL.
- Select the application-database driver during first-time setup.
- Plan, copy, verify, activate, and roll back an application-database migration from the administrator interface.
- Resume interrupted copies safely and verify source stability before activation.
- Fence normal web, queued, scheduled, and native-client control activity during copy, cutover, and rollback while preserving an authenticated recovery path for administrators.
- Keep migration credentials encrypted and out of browser props, audit metadata, and command output.

### Safer SQL governance

- Configure governed SQL statement families and review candidate statements from the administration interface.
- Recognize safe PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` statements within the normal insert policy.
- Preserve the audited Deployment Batch emergency fallback for unsupported single statements while continuing to block administrative, file-access, security-management, procedural, transaction-control, multi-statement, and `EXPLAIN ANALYZE` SQL.
- Reject MySQL executable comments and optimizer hints that could hide executable behavior from policy classification.

### Security and operational hardening

- Encrypt and authenticate native proxy control requests and responses.
- Require a deployment-controlled token before a fresh installation can select its database or create the first owner.
- Preserve a completed-setup sentinel and serialize initial ownership creation.
- Bind bundled HTTP origins and development service ports to loopback by default.
- Neutralize spreadsheet formulas in CSV exports and sanitize application-database migration failures.
- Verify both the selected control database and Redis in readiness checks.

### Cleaner administration

- Use independently collapsible Administration and Account navigation groups.
- Organize administrative pages under Access & identity, Security & policy, Application, and Governance.
- Expose SSO Providers directly under Security & policy.
- Move completed application-database plans into collapsed migration history.
- Contain wide query results inside their own horizontal scrolling region instead of shifting the entire execution history page.

## Production deployment changes

v0.2.0 uses three core services:

1. The application image runs the embedded Caddy/FrankenPHP origin, Laravel Octane, Horizon, and the scheduler.
2. Redis stores queues, sessions, cache, Horizon metadata, and immediate native-lease revocation state.
3. The private native proxy handles PostgreSQL/MySQL protocol connections and the same-origin tunnel route.

PostgreSQL or MySQL may additionally be selected as the control database through an external managed endpoint or an optional isolated Compose profile.

Production Compose no longer supplies an implicit application image version. Pin both images to the same release:

```dotenv
CRUCIBLE_IMAGE=hephaestus/crucible-db:0.2.0
CRUCIBLE_NATIVE_IMAGE=hephaestus/crucible-db-native:0.2.0
```

The release workflow also publishes `latest` for evaluation and convenience, but production deployments should continue to use the immutable `0.2.0` tag or an image digest.

Read the complete [production deployment and upgrade guide](../operations/production.md) before recreating a deployment.

## Upgrade from v0.1.0

1. Back up the application storage volume and Redis before changing containers.
2. Preserve the existing `APP_KEY`; changing it makes encrypted credentials and settings unreadable.
3. Compare the current environment with `.env.production.example`, including the native proxy control key and both pinned image variables.
4. Pull and recreate the stack with the v0.2.0 application and native-proxy images.
5. Wait for the application and Redis readiness checks, then verify login, queue processing, scheduling, and one governed database request.
6. Introduce native-client access only after reviewing its private-network topology and operating procedures.

Existing SQLite control data remains supported. Migrating that data to PostgreSQL or MySQL is optional and should be performed through the fenced administrator workflow after the upgraded application is healthy.

## Release artifacts and verification

The tag workflow publishes:

- Multi-architecture `linux/amd64` and `linux/arm64` application and native-proxy images with OCI provenance and SBOM attestations.
- Crucible CLI archives for macOS, Linux, and Windows on `amd64` and `arm64`.
- Linux `.deb` and `.rpm` packages.
- Checksums, a keyless Sigstore checksum bundle, archive SBOMs, and GitHub build provenance.
- An updated Homebrew cask in `adiwidia-dev/homebrew-tap`.

Before publication, the release gate repeats the application suite, cross-driver application-database matrix, native race suite, protocol integration matrix, image smoke tests, GoReleaser validation, artifact checksums, signatures, archives, packages, and SBOM verification.

## Compatibility notes

- PostgreSQL 14, 15, 16, 17, and 18 are qualified in automated native-client CI.
- MySQL 8.0 and 8.4 are qualified in automated native-client CI.
- DBeaver and pgAdmin with PostgreSQL, and DBeaver and MySQL Workbench with MySQL, have exploratory simple-query evidence but still require the complete versioned desktop-client checklist before being labelled fully supported.
- MySQL server-side `KILL` and `KILL QUERY` remain intentionally blocked because the leased target principal is not granted administrative privileges. Client cancellation that depends on a second server-side kill connection therefore remains limited.
